1. ブックマーク永続化モジュールに seam を切り、AppDelegate オーケストレーションをテスト可能にする

Strong
Files
Sources/VideoFileValidator.swift（181行・public static ×12）, Sources/AppDelegate.swift, Sources/PlaylistPersistence.swift
Problem
VideoFileValidator は static enum で、interface（12 メソッド）が implementation（各 3〜10 行の UserDefaults / bookmark ラッパー）とほぼ同じ複雑さの浅い namespace。seam が無いため、これを直接呼ぶ handleVideoSelected / handleVideoCleared / handleDisplayToggled / buildDisplayStates という AppDelegate の 4 つのオーケストレーション経路が実 FS と UserDefaults.standard に縛られ、全て未テスト。さらに stale bookmark の再保存が load() の中で暗黙に走る（interface に現れない副作用）。
Solution
12 個の static メソッドを「画面ごとのブックマーク台帳」という 1 概念に再設計する。DisplayBookmarkStore のような protocol（save / resolve / clear / isDisplayEnabled 程度の 4〜5 メソッド）を seam とし、URL 正規化・stale 再保存・キー管理を implementation 側に沈める。AppDelegate と PlaylistPersistence には init で注入する。2 つ目の adapter（in-memory fake）がテストで成立した時点で seam が real になる。
Benefits
Leverage: 呼び手は「URL を渡せば永続化される」だけ知ればよく、bookmark data・/private/ 正規化・stale 処理を知らなくてよい。Locality: bookmark 関連バグ（knowledge.md に 3 件記録あり）の修正先が 1 ファイルに集中する。Tests: AppDelegate の動画選択→保存→reload→menu 更新という連鎖が fake store で初めて検証可能になる。interface が test surface になる。

BEFORE — 浅い: interface ≒ implementation

implementation

static 呼び出しが AppDelegate / PlaylistPersistence / DropDestinationView の 3 箇所に散在。fake 差し替え不可。

AFTER — 深い: 小さい interface の裏に挙動を集約

adapter ×2（URL/UserDefaults 実装 + テスト用 in-memory）で real seam に。stale 再保存も implementation 内の不変条件として文書化。

2. PlaybackSession を production に統合する — テスト済みの dead module を生かす

Strong
⚠ tasks/todo.md の P1 項目（PlaybackSession の AppDelegate 統合）と同一スコープ。レビューとして再確認した結果、friction は実在し優先度は妥当。
Files
Sources/PlaybackSession.swift（31行）, Sources/AppDelegate.swift, Sources/WallpaperWindowController.swift, Sources/RotationEngine.swift
Problem
PlaybackSession は token 発行と playlist 前進を司る純粋値型で、14 個の単体テストを持つが、production からの参照ゼロ。「テストのために抽出された純粋関数」の典型で、実際のバグが潜む場所——AppDelegate が完了通知を受けて全 controller に次 item を配る配線——は存在すらしない。locality が無く、テストは将来機能の正しさを検証して false confidence を生んでいる。showPlaylistEditor() も call site ゼロ。
Solution
AppDelegate に PlaybackSession を持たせ、playlist 変更→beginPlayback()→全 controller へ load、完了通知→consume()→advance→persist→UI 更新、という 1 本のオーケストレーション経路を作る。knowledge.md に既に蓄積された token 設計知見（screen 再構成では token 再発行しない、等）をこの経路の不変条件として実装する。
Benefits
Locality: 「再生ライフサイクル」を理解するのに今は 6 ファイルを往復するが、配線後は AppDelegate の 1 経路 + PlaybackSession の不変条件に集約される。Tests: 既存の 14 テストが初めて実挙動の保証になる。fake controller での AppDelegate 統合テスト（todo P1 記載）が書ける。

3. 表示設定（Dim / Gravity / PowerSaving）を 1 つの設定モジュールに深める

Worth exploring
Files
Sources/DimLevel.swift, Sources/VideoGravity.swift, Sources/PowerSavingMode.swift, Sources/StatusMenuController.swift, Sources/AppDelegate.swift
Problem
各 enum が自分の永続化層を兼ね、UserDefaults.standard・callback で飛ぶ一時値・新画面追加時の再読込という3 つの source of truth が並走する。象徴的なのが onPowerSavingModeChanged: callback は値を運ばず（() -> Void）、AppDelegate が PowerSavingMode.saved をもう一度 UserDefaults から読む。seam が無いため lifecycle テストは UserDefaults.standard を手動 defer 掃除しており（knowledge.md にも競合の学びが複数）、menu の選択状態は init 時 snapshot のまま stale になり得る。
Solution
「壁紙設定」という 1 モジュール（例: WallpaperSettings）に深める。in-memory の現在値を単一の所有者が持ち、永続化は implementation 内の関心事に沈める。StatusMenuController は値を変更要求として流すだけ、AppDelegate（または settings 自身）が controller 群へ伝播。enum の saved/save() パターンは廃止。knowledge.md の「設定値 enum パターン」の更新が必要。
Benefits
Locality: 「今の設定は何か」に答える場所が 1 つになり、stale snapshot / 再読込クラスのバグが構造的に消える。Tests: suite-scoped defaults の手動掃除が不要になり、settings を fake にして AppDelegate / menu のテストが決定的になる。ADR の schedule 機能（clockProvider 注入方針）とも親和。

4. RotationEngine の token 型を壁紙ウィンドウの interface から追い出す

Worth exploring
Files
Sources/AppDelegate.swift（WallpaperWindowControlling protocol, L15付近）, Sources/WallpaperWindowController.swift, Sources/RotationEngine.swift
Problem
WallpaperWindowControlling.load(...) の引数に RotationEngine<PlaylistItem>.PlaybackToken が現れ、ウィンドウ controller の seam が rotation 実装の内部型に依存している。controller は playlist を知らないはずなのに、interface が「caller が知るべきこと」として rotation の generation 概念を要求する典型的な seam 越え leak。現 production では常に nil。
Solution
controller 側の interface には generic でない不透明な再生識別子（例: PlaybackContextID — Equatable のみ）を置き、RotationEngine の token からの変換は AppDelegate（playlist を知る側）で行う。候補 2 の配線と同時に実施するのが自然。
Benefits
Leverage: controller の caller は「同一性比較できる ID」だけ知ればよい。Locality: rotation の token 設計変更（knowledge.md に学び多数）が controller protocol に波及しなくなる。fake controller のテスト記述も単純化する。

5. PlaylistEditorActionBridge（pass-through adapter）を畳む

Worth exploring
Files
Sources/PlaylistEditorWindowController.swift（413行）, Sources/AppDelegate.swift（configure(editor:) L302–330）
Problem
8 つの編集 callback が 3 回宣言されている: controller の computed property、PlaylistEditorActionBridge の stored closure、AppDelegate での代入。bridge は deletion test で複雑さが完全に消える純粋 pass-through——挙動を一切足さない hypothetical seam。callback を 1 本足すたびに 3 ファイル 3 箇所の編集が要る（locality 欠如）。
Solution
個々の closure ×8 ではなく、「playlist 編集操作」を 1 つの interface（例: PlaylistEditing protocol — delete / move / setCurrent / update 系をメソッドとして持つ）に深め、AppDelegate を adapter としてエディタに渡す。bridge は削除。editor 側の test double は protocol 実装 1 つで済む。
Benefits
Locality: 操作追加が「protocol に 1 メソッド + AppDelegate に 1 実装」で完結。Tests: 8 closure の個別差し込みではなく spy 1 個でエディタ→操作の検証ができる。ADR の schedule 機能で予定されている callback 追加（onScheduleConfigChanged 等）もこの interface に乗せられる。

6. StatusMenuController の test surface を ForTesting backdoor から interface に移す

Speculative
Files
Sources/StatusMenuController.swift（455行・ForTesting ×10, L413–455）, Tests/.../StatusMenuControllerTests.swift
Problem
10 個の ForTesting プロパティ/メソッドは「interface が test surface になっていない」ことの直接的な兆候。テストは NSMenuItem の個数・identity という implementation 詳細を検証しており、メニューの見た目を変えるだけで壊れる。一方、ユーザー操作→callback 発火という本来の挙動（selectDimLevel → save + onDimLevelChanged の連鎖など）は未テスト。
Solution
メニューを「menu state（何が表示・選択・有効か）→ NSMenu への描画」の 2 層に分け、state を interface として公開する。テストは state を検証し、ForTesting backdoor を段階的に削除。候補 3（設定モジュール）が先にあると state の定義が自然になる。
Benefits
Tests: 実装替えに耐えるテストになり、未テストの action→callback 連鎖が state 遷移として検証できる。Locality: 差分更新ロジック（knowledge.md の NSMenu 差分更新の学び）が描画層 1 箇所に集中。ただし NSMenu 周りの作り直しコストが大きく、candidates 1–3 より優先度は低い。

🏁 Top recommendation: 候補 1（ブックマーク永続化の seam）から着手

候補 2（PlaybackSession 統合）が機能的には最重要だが、その AppDelegate 統合テストを書くには bookmark resolve が fake にできることが前提になる。候補 1 は候補 2・3 の test surface を先に作る土台であり、 interface は今より小さくなる方向（12 → 4〜5 メソッド）なので回帰リスクも低い。 順序としては 1 → 2（+4 を同時に）→ 3 → 5 → 6 を推奨。 候補 4 と 5 は候補 2 の配線作業と同じファイルを触るため、同一ブランチでまとめると差分が読みやすい。
